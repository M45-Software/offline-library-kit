# Instructions for building an offline library

This project is a reusable starting point. Work with the operator to choose the collection, storage and devices. Do not assume a particular machine, region, equipment model, drive label, access point name or user account.

1. Inspect existing drives, available space, mounts and running transfers before writing. Confirm the target filesystem and marker; never format, repartition or overwrite a drive without explicit authorization. Keep writes to slow archive drives serialized, and stage downloads on suitable storage where possible. Avoid two processes writing the same file.
2. Locate original publishers and verify current versions, licenses, checksums, sizes and compatibility. Never guess a publisher hash. Distinguish publisher checksums from locally generated baselines. Respect access restrictions; do not bypass them.
3. Ask which medical, survival, repair, food, farming, education and map references fit the operator's needs. Avoid presenting user-contributed or old guidance as verified safe or comprehensive. Record the date, source and meaningful omissions. Do not commit downloaded or scraped material to this repository unless the operator explicitly asks for a specific item and it is appropriate to redistribute.
4. Obtain suitable offline readers for the target systems. Copy verified files, use per-file checksums, and preserve or inspect failures. Verify available storage before transfers. A completed download is not proof of a usable offline library.
5. For a Pi build, identify the model, display, card and OS; use account and network settings chosen by the operator. Default to a plain black desktop background; put connection QR codes on the library page rather than the wallpaper. Do not store passwords, QR images containing credentials, personal paths or generated device identifiers in version control. Never expose private backups on a network share. Test the home page, searching, PDFs, QR scanning and local sharing on the actual device without external internet; describe untested functions accurately.
6. Validate restore from each archive, confirm relevant file and link integrity, and record what was actually tested. Tell the operator about stale material, incomplete coverage, checksum discrepancies and missing software. Avoid declaring complete until requested functionality is verified.

This repository intentionally excludes personal data and content. Inspect the actual diff, Git history, file names, metadata and secrets before publishing. Do not publish private information, scraped archives, credentials or binaries. Preserve the operator's source data and never delete a questionable copy merely to save space.
